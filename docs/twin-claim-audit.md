# Twin claim audit

This audit distinguishes checks that can be reproduced from this snapshot from research-data claims that remain unverified here. It reviews implementation and evaluation-protocol source. This portfolio contains no participant records, benchmark result files, or fitted participant models.

| Claim | Status in this snapshot | Evidence and limit |
| --- | --- | --- |
| The differentiable simulator agrees numerically with its `simglucose` reference under matched synthetic inputs. | Verified for the included check. | Two virtual subjects, six hours each: maximum pointwise difference 1.34 mg/dL and pooled RMSE 0.53 mg/dL. This checks numerical implementation agreement, not human-data fit or forecast validity. See [`twin_numerical_check.py`](../scripts/twin_numerical_check.py). |
| The fitter can serialize a fit and produce held-out replay diagnostics on artificial records. | Verified by focused synthetic tests in this snapshot. | The tests use generated records and cover fit serialization, the holdout diagnostic fields, delivery gaps, explicit zeros, and a paired intervention direction. They do not establish performance on people. See [`test_twin.py`](../twin/tests/test_twin.py) and [`fit.py`](../twin/t1d_twin/fit.py). |
| The twin improves glucose forecasting or low-glucose prediction over a neural baseline on research datasets. | Not verified for this snapshot. | The development README contains aggregate benchmark claims, but the score files and participant data are not included here and those results were not independently regenerated for this portfolio. I therefore omit those numbers from the public twin description. |
| The published benchmark harness compared the same held-out sequences for the twin and T1DSim_AI. | Protocol reviewed in development source; not rerun here. | The harness exports training flags from the twin's fitted-day split, uses T1DSim_AI's `SequenceSelection` for train and test windows, and scores the twin on the saved test windows. The benchmark scripts are not included in this portfolio snapshot. This source review supports the stated protocol, not the correctness of any saved benchmark result. |

This aligns sensor-noise injection at scoring time; it does not give the baseline the twin's posterior uncertainty or establish calibrated probabilities. The evaluation scripts and outputs are not packaged here. |
| The settings experiments identify real-world effects of changing insulin settings. | Open research question. | The included experiment code pairs posterior samples across arms and scales recorded delivery. Synthetic tests can check known effects in the simulator. They cannot establish counterfactual validity in real people; closed-loop controller response is not represented by recorded-delivery replay. ## Benchmark protocol notes

In the development source, `fit_twin` uses a chronological prefix for fitting and reserves the requested trailing days for holdout evaluation. Base-subject and event-clock screening use the fitting days. The T1DSim_AI export maps those fitted days to its training flag, and the train script creates held-out five-hour sequences with the baseline package's sequence selector. The scoring script consumes those same test-sequence origins and targets for the twin. Relevant development-source files are `t1d-twin/t1d_twin/fit.py` and `t1d-twin/scripts/benchmark_t1dsimai_{export,train,score,report}.py`; these benchmark scripts are not included in this portfolio snapshot.

For low events, the harness defines probabilities by adding sensor noise to each trace. The baseline is deterministic, so the report code applies the twin fit's CGM residual-noise estimate to repeated baseline traces before scoring. That is a noise-matched evaluation layer, not a matched model-uncertainty treatment. The empirical aggregate results need their saved score provenance and a reproducible rerun before they can support a comparative claim.

The bundled synthetic recovery entry point is `twin/scripts/twin_recovery.py`. A short invocation appears in [the twin overview](digital-twin.md); it checks execution on generated records only.
